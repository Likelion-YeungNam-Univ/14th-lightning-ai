## 1. 아키텍처 결정: FastAPI 단일 서버

**결정: 스프링 없이 FastAPI 하나로 서버 + AI + 배치를 전부 구현한다.**

근거:

1. **이 서비스의 데이터 계층이 파이썬 생태계에 있다.** 종목 마스터(B1)의 현실적 해법이 `FinanceDataReader`/`pykrx`(파이썬 전용)이고, DART corpCode 파싱, 임베딩, LLM SDK까지 전부 파이썬이 가장 짧다. 스프링을 쓰면 이 부분을 별도 파이썬 프로세스로 빼야 해서 결국 2-레포 문제가 돌아온다.
2. **서버의 성격이 단순하다.** 인증은 모의 구현, 도메인은 CRUD + 조회, 트래픽은 시연 규모. 스프링의 강점(대규모 도메인, 복잡한 트랜잭션, 팀 규모 확장)이 필요한 지점이 없다.
3. **배포 리스크 최소화.** 단일 Docker 이미지 하나만 올리면 끝. 서비스 2개면 배포·CORS·서비스 간 인증·장애 지점이 전부 2배가 된다. 해커톤에서 "발표 전날 연결이 안 됨"의 대부분이 여기서 나온다.
4. 스프링 익숙함의 손해는 제한적 — FastAPI의 라우터/서비스/스키마 구조는 스프링의 Controller/Service/DTO와 1:1로 대응된다. 아래 구조 가이드 참고.

주의점 (스프링 사용자가 FastAPI에서 흔히 밟는 지뢰):

- **async 함정**: 전부 `async def`로 쓰다가 동기 DB 호출로 이벤트 루프를 막는 사고가 흔하다. **원칙: DB 접근 엔드포인트는 일반 `def`로 작성**(FastAPI가 스레드풀에서 실행) + 동기 SQLAlchemy. 외부 API를 병렬로 부르는 수집기만 `async` + `httpx`.
- **스케줄러와 워커 수**: APScheduler는 프로세스 안에서 돌기 때문에 uvicorn 워커를 2개 이상 띄우면 배치가 중복 실행된다. **워커 1개 고정**(시연 트래픽엔 충분).
- 마이그레이션은 Alembic 없이 시작해도 된다 — 초기엔 `create_all` + 시드 스크립트로 충분, 스키마가 안정되면 도입.

## 3. RAG 설계 (F-4.8) — 심사 설명 포인트 포함

파이프라인 (교과서적 구성이라 심사에서 설명하기 좋다):

```
[적재 - 1회성 스크립트]
한국은행 경제금융용어 700선 ─┐
                              ├→ 용어/유형 단위 청킹 → 임베딩(text-embedding-3-small)
DART 공시유형 해설 20~30건 ──┘        → pgvector 저장 (knowledge_chunk)

[검색 - 요청/배치 시]
질의(드래그한 용어 / 공시 유형·제목) → 임베딩 → 코사인 유사도 top-3
  → 유사도 하한 통과분만 프롬프트 컨텍스트로 주입 → OpenAI 생성
```

사용처 2곳:

1. **용어 풀이(F-4.4)**: 드래그 텍스트로 700선을 검색해, 한국은행 공식 정의를 근거로 문맥 맞춤 설명을 생성. "설명의 근거가 한국은행 공식 용어집"이라는 점이 서비스 콘셉트(공공 데이터 신뢰)와 정확히 맞물린다.
2. **공시 요약(F-4.1)**: 공시 유형 해설을 검색·주입해, 제목만으로 요약할 때의 환각(없는 금액·조건 생성)을 구조적으로 억제.

심사 질의응답 대비 — 한 줄 답변:

- *무엇을 RAG했나?* → 한국은행 「경제금융용어 700선」 + DART 공시유형 해설을 자체 지식베이스로 구축.
- *왜 파인튜닝이 아니라 RAG인가?* → 근거 출처를 사용자에게 제시할 수 있고(신뢰 콘셉트), 데이터 갱신이 적재만으로 끝나며, 해커톤 기간·비용에 맞다.
- *검색은 어떻게?* → 질의·문서를 같은 임베딩 공간에 놓고 pgvector 코사인 유사도 top-3, 유사도 하한 미달이면 주입하지 않음(억지 근거 방지).
- *환각은 어떻게 막나?* → RAG 근거 주입 + 숫자 토큰 후처리(F-4.1.3) + 금지 표현 가드레일(F-4.5) + 시연 종목 전수 검수·잠금(F-4.7)의 4중 장치.

## 4. 시스템 구성

```
[사용자] ── Vercel(프론트) ── /api rewrite ──> FastAPI (단일 프로세스)
                                                ├─ routers/   세션·종목·카드·저장·용어·이벤트
                                                ├─ services/  비즈니스 로직
                                                ├─ collectors/ DART·정책브리핑·ECOS·FRED·YouTube·KRX
                                                ├─ ai/        요약·라벨·문장·용어풀이·가드레일·RAG
                                                ├─ scheduler  APScheduler (06:00 배치, 주 배치)
                                                └─ PostgreSQL + pgvector
```

원칙 (명세서와 동일): 사용자 요청 경로에서 외부 API·LLM을 부르지 않는다(유일한 예외: 용어 풀이). 수집 → 생성 → DB 적재는 전부 배치/온디맨드에서 끝내고, 조회 API는 DB만 읽는다. 이 구조 덕에 시연 중 외부 API가 죽어도 화면은 살아 있다.

## 5. 개발 순서 (7단계)

프론트가 일찍 붙을 수 있도록 조회 API의 목(mock) 응답을 P2에서 먼저 고정한다.

| 단계 | 내용 | 완료 기준 |
| :---- | :---- | :---- |
| **P0 기반** (착수일) | 레포/도커/DB 셋업, 키 6종 발급, **KRX 마스터 적재 + corpCode 매핑 실측(V2), 정책브리핑 부처명 대조(V1)**, 업종 12분류 매핑표 작성 | `stock_master`가 채워지고 삼성전자 corp_code가 조회된다 |
| **P1 세션·종목** | F-1 전체, F-2 전체 (검색·추가·삭제·순서·기본종목) | 쿠키 세션으로 종목 CRUD가 돈다. 비로그인 401 동작 |
| **P2 조회 골격** | F-5 `/cards` 공통 스키마 확정 + 더미 데이터 응답 | 프론트가 이 시점부터 실제 스키마로 개발 시작 |
| **P3 수집기 (국내)** | 국내 수집 전체 (DART·정책브리핑·ECOS·FRED·유튜브 + 쿼터 방어 + 배치, v3 F-4.1~4.5·4.8~4.10) | 배치 1회 실행으로 국내 탭 원자료가 DB에 쌓인다 |
| **P4 AI 가공** | 요약·라벨·연결 문장·가드레일 (v3 F-5.1~5.3·5.5~5.7) — structured output | `/cards`가 실데이터+생성물을 반환. 시연 종목 검수 1차 |
| **P🌏 해외 축** | 화이트리스트·CIK 매핑(F-3.2), 구분 도메인(F-2), SEC·Federal Register 수집(F-4.6~4.7), 해외 요약·라벨 | **국내 축(P1~P4) 완성 후 착수** — 지연 시 국내만으로 시연 성립. 완료 기준: 해외 종목 1개로 3개 탭(유튜브·공시·규제)이 뜬다 |
| **P5 RAG·저장** | 지식베이스 적재(확정사항 5절), 용어 풀이(F-5.4), 저장/스냅샷(F-7) | 드래그 용어 풀이가 700선 근거로 동작. 저장→저장됨 탭 |
| **P6 마감** | F-7.2 이벤트, F-1.5 리셋, F-4.7 잠금, 배포, 캐시 워밍(F-3.5.2), 리허설 | 배포 URL에서 시연 시나리오 전체가 재현된다 |

**팀 분담 제안** (백엔드 2인): 한 명은 P1→P2→F-6(도메인/API 축), 한 명은 P0 데이터→P3→P4→P5(수집/AI 축). P2의 스키마 확정이 두 축과 프론트의 합류 지점.

## 6. 심사 기준 대비 — PM에게 전달할 것

트랙 배점이 **고객 구체성 10점 + 지불 의사 검증 10점**인데, 이 20점은 개발이 아니라 **문서·인터뷰 보강**으로 얻는 점수다. PRD 기준 현재 상태:

| 항목 | 현재 PRD | 부족한 점 | 보강 방법 |
| :---- | :---- | :---- | :---- |
| 고객 구체성 | 페르소나(김도희, 25세 간호사, 투자 6개월) + 인터뷰 4명 — 좋은 출발 | 심사 문구가 "**어느 지역에서** 누가 쓸지 실제 인물이 그려질 만큼"인데 지역·생활 맥락이 없다 | 페르소나에 지역·근무 형태·투자 채널·하루 중 사용 시점(출근 전 뉴스 확인 등)을 추가. 인터뷰이 4명의 프로필을 익명화해 부록으로 |
| 지불 의사 검증 | **없음 — 현재 0점 위험.** 인터뷰는 '불편'을 검증했지 '돈을 낼 이유'를 검증하지 않았다 | 가격 가설도, 지불 접점 증거도 없다 | 해커톤 전까지 가능한 것: ① 기존 인터뷰이 재접촉 + 신규 5~10명에게 지불 의사 질문(월 ○○원이면 쓸 것인가, 무엇이면 돈을 내겠는가) ② 가격 가설 수립(예: 무료 + 종목 무제한/알림 프리미엄) ③ 사전 등록 랜딩페이지로 전환율 측정. 이 중 ①은 이번 주에 시작해야 한다 |

발표에서 기술 어필 포인트: RAG(3절 질의응답), 환각 4중 방어, "사용자 경로에서 외부 API를 부르지 않는" 장애 격리 구조, 라벨을 매수 신호로 오용하지 못하게 막은 스키마 설계.

## 7. 리스크 (기술)

| 리스크 | 대응 |
| :---- | :---- |
| KRX 라이브러리(비공식) 필드 변경·차단 | P0에서 실측(V2). 실패 시 대안: 공공데이터포털 금융위 주식시세정보 API |
| 유튜브 쿼터 소진 | 종목 단위 dedupe(C9) + 자체 카운터 + 80% 컷 + 시연 종목 워밍. 발표 당일 배치는 시연 종목만 |
| 금통위 결정 요지 확보 실패 | 수동 시드가 1차 계획(C3)이므로 실패 개념 없음. 자동화는 보너스 |
| LLM 비용 | 생성은 자료당 1회 + DB 재사용 구조라 총량이 작다(종목 30개 × 카드 20건 수준). 용어 풀이만 레이트리밋(F-7.3) |
| 배치 중복 실행 | 워커 1개 고정(F-7.7). 배치 시작 시 DB 락 플래그로 이중 안전장치 |
| 시연 중 재생성으로 검수 무효화 | `locked` 잠금(F-5.7) + 시연 전 배치 비활성 옵션 |
| **해외 축 추가로 인한 일정 압박 (v3)** | 국내 우선 전략(P🌏는 P4 뒤) + 화이트리스트 15개로 축소 시작 + SEC·Federal Register는 키 불필요라 착수 비용 낮음. 최악의 경우 해외 축을 빼도 국내만으로 시연 성립 |
| SEC User-Agent 미설정으로 차단 | `SEC_USER_AGENT` 환경 변수 필수화 — 수집기가 미설정 시 즉시 에러로 알림 |
